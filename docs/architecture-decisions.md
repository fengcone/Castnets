# Castnets M0 架构决策

## 1. 两条时间线，不篡改主播放进度

主时间线属于播放器；Conversation Branch 是锚定 `episode_id + anchor_ms` 的支线。Branch
保存提问、结构化回答、证据快照和恢复位置。追问追加到同一支线，但不会推进主播放时间。
显式“继续”把支线从 `active` 改为 `resumed`，恢复位置在创建时计算，因此恢复请求天然幂等。

SQLite 写入使用事务；追问的“检查 active 状态 + 追加 + 保存”放在同一个
`BEGIN IMMEDIATE` 事务里，避免并发追问相互覆盖或与恢复操作交叉。

## 2. 时间精度是数据，不是措辞约定

内容有三个状态：

- `chapters_only`：只有 RSS 章节，能定位主题区间，不能声称知道当前句子。
- `transcript_unaligned`：有整期文本，但没有可靠音频时间；只允许关键词检索相关片段。
- `transcript_timed`：每段有导入者提供的 `start_ms` / `end_ms`；M0 仍提示尚未校验音频版本误差。

每个来源另有 `timing`，回答上下文另有 `precision`。未对齐文本不会被插值成伪时间戳；检索
只读当前锚点之前最多 90 秒的 timed segment，避免把尚未播放的内容作为“刚才”上下文。

## 3. AI 是解释者，不是节目人物

原始音频提供真人感。回答者必须以独立解释层出现，来源和限制随回答保存。M0 的
`MockProvider` 只覆盖少量人工词条；未覆盖时返回结构化失败，不根据章节标题或模糊片段猜测
嘉宾意图。以后接入模型时，Provider 可以替换，但 `Branch` / `Answer` / `Context` 契约保持稳定。

## 4. 上下文按需路由

目标上下文分四层：

1. 用户明确授权的个人上下文；
2. 当前时间附近及整期节目内容；
3. 节目、主持人和嘉宾资料；
4. 通用知识。

M0 只落地第 2 层和一个可审计的第 4 层演示词表。未实现的层不会用空壳数据冒充。未来路由器
应先判断问题需要哪些层，再检索并记录实际使用的来源；不默认把个人资料或整期文本全部发送给
模型。

## 5. RSS 与转写分离

RSS 是节目、单集、音频 URL、时长和章节的事实来源。转写是可替换的附加内容，其
episode 标题必须唯一匹配，或者 timed payload 必须显式携带同一个 `episode_id`。重新同步 RSS
不会覆盖已经导入的逐字稿。

网络摄取只接受 HTTPS，并设置大小和超时上限。HTTP 服务不接受任意抓取 URL，避免把本地
API 变成 SSRF 入口；feed 摄取由 CLI/后台作业完成。

## 6. Android 面向 `/v1`，OpenAPI 是契约

Android 客户端不读取 SQLite，也不复刻恢复位置计算。它只使用 `/v1` JSON 资源和
OpenAPI 3.1 schema。所有对象字段由服务端 dataclass 生成 schema，错误统一为
`{"error":{"code":"...","message":"..."}}`。破坏性字段变更需要新的 API 版本。

当前服务器仅用于本机开发：loopback-only、无认证、无 TLS、请求体上限 16 KiB。生产后台需要
独立补充身份认证、授权、速率限制、可观测性、迁移机制和隐私数据保留策略。

## 7. M0 的完成标准与后续风险

完成标准是：离线样例能从 RSS 建立节目和单集，显示诚实精度，创建并持久化支线，追加追问，
幂等恢复，并通过 CLI 与 HTTP 契约读写同一数据。

尚未解决的风险包括：真实长音频的转写/说话人/时间对齐质量；feed 与音频版本变化；模型回答
的事实性、延迟和成本；耳机按键在 Android 机型与后台限制下的一致性；TTS 与原音频焦点切换；
用户上下文的授权、删除和最小化；线上 API 的安全与数据迁移。千问 AI 眼镜适配在手机闭环验证
之后再进入范围。
