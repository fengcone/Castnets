# Castnets 项目长期上下文

> 最近核对：2026-09-27
> 适用范围：产品判断、架构取舍、开发任务启动、阶段验收
> 事实约定：凡写“已实现”的内容，均应能在当前仓库代码或测试中找到依据；愿景、假设和竞品判断不等于已实现能力。

## 一句话定义

Castnets 是一个面向中文播客的、Android 优先的“可打断式收听”个人产品：用户在节目播放到某个具体时刻时暂停并提问，系统基于此刻之前的节目上下文和经过授权的个人上下文回答，允许继续追问，最后明确回到原节目时间线。

Castnets 与 Chatnets 是相邻产品：Castnets 负责收听现场的打断、解释和返回；Chatnets 负责用户长期积累的个人知识与上下文。二者可以协同，但首版不应把每次收听自动扩张成复杂知识工程。

## 用户真正要解决的问题

目标用户会在走路、通勤、做家务或乘车时收听长篇中文对谈。真正的痛点不是“没有摘要”，而是：

- 听到陌生概念、人物、事件或一句值得追问的话时，问题只在当下最清楚；
- 解锁手机、定位文字、搜索和整理会中断收听，也很容易让问题流失；
- 通用搜索不知道正在播放的内容和时间点，整集聊天又容易把后文泄漏给用户；
- 得到解释以后，用户还需要无摩擦地回到节目，而不是重新寻找播放位置。

Castnets 的核心闭环因此是：

`播放节目 → 在当前时刻打断 → 提问 → 得到简短回答 → 必要时追问 → 明确继续 → 小幅回退后恢复播放`

它不是一个单纯的转写、摘要、划线或通用聊天工具，也不试图用 AI 替代主播和嘉宾。

## 产品交互模型

### 主时间线与 Conversation Branch

节目播放是主时间线。每次提问创建一条 Conversation Branch，至少绑定：

- podcast / episode；
- 打断时的播放位置 `anchor_position_ms`；
- 用户问题与后续多轮对话；
- 回答使用的上下文精度和来源；
- 回到主时间线时由服务端给出的 `resume_position_ms`。

标准交互应满足：

1. 用户触发提问后，播放器立即暂停并冻结当前 episode 与时间点。
2. 系统先回答当前问题，允许在同一 Branch 中继续追问。
3. AI 以“解释者”身份说话，不冒充节目主播、嘉宾或创作者。
4. 用户明确选择“继续播放”后才离开 Branch。
5. 恢复位置由服务端决定；当前策略是锚点前约 5 秒，帮助用户重新进入原语境。

服务端给出的恢复位置是最终值。客户端不得再次自行减去 5 秒，否则会造成重复回退。

### 轻交互与深交互

Castnets 需要同时支持两种强度，但不能混为一个界面：

| 模式 | 适用状态 | 目标交互 |
| --- | --- | --- |
| 轻交互 | 走路、通勤、双手被占用 | 一次按键打断、语音提问、短语音回答、继续或取消；尽量不看屏幕 |
| 深交互 | 用户已停下或主动打开手机 | 查看文字、来源和上下文，继续多轮追问，回看 Branch，选择是否沉淀到 Chatnets |

首选触发方式是耳机按键或等价的硬件动作，不以唤醒词为首发入口。原因是它更私密、确定性更高，也更容易形成“按一下即可打断”的肌肉记忆。

### 驾驶安全边界

驾驶场景是产品愿景中的重要约束，但不是当前版本已经具备的能力。

- 驾驶员不应在行驶中打字、阅读回答或操作多层界面。
- 当前 M1 依赖屏幕按钮和文字输入，因此不得描述为“可安全驾驶使用”，也不应在真实驾驶中进行交互测试。
- 面向驾驶的后续版本至少需要可靠的耳机/车载按键、语音输入、短语音输出、明确的继续/取消指令、超时策略和锁屏状态验证。
- 复杂回答、来源阅读、知识整理等深交互必须留到车辆安全停稳后。
- 产品指标不能只看问答成功率，还要看误触发、分心时长、恢复失败和音频焦点异常。

## 四层上下文模型

回答质量不是来自把所有资料一次性塞给模型，而是来自按问题路由到正确的上下文层，并保留可解释的来源。

1. **个人上下文（Chatnets）**：用户明确授权的个人笔记、已学概念、过往问题和偏好。它用于回答“这和我之前学过的什么有关”等个人化问题。
2. **当前时刻与本集内容**：当前 episode、播放时间点、此刻之前的定时转写、章节和节目元数据。这是收听现场问题的默认主上下文。
3. **节目、主播与嘉宾上下文**：节目背景、主播/嘉宾公开资料、往期内容及可信来源。它用于人物、立场和系列背景问题。
4. **通用知识**：当节目本身不足以解释概念时使用的外部或模型知识，并应与节目原话区分。

路由原则：

- 默认先取最小且最相关的层，不盲目拼接四层内容；
- 不把节目后文作为当前时刻的上下文，避免剧透和因果倒置；
- 定时转写可以支持精确时间窗口，章节只能支持章节级判断，未对齐全文只能支持弱匹配；
- 上下文不足时明确说不足，不伪造精确引文、时间点或嘉宾观点；
- 回答记录应能说明使用了哪一层、哪种精度和哪些来源。

当前 M0 主要实现了第 2 层，并用一个确定性的术语表模拟了极小部分第 4 层。Chatnets 个人上下文、节目/主播/嘉宾知识层及真正的多层路由尚未实现。

### Chatnets 的角色与边界

Chatnets 是可选、私有、经过授权的个人上下文来源，不应成为 Castnets 使用的前置条件。

首阶段联动只需要验证两件事：

- Castnets 能否读取与当前问题直接相关的少量个人上下文；
- 用户主动选择时，能否把真实问题、episode、时间锚点和必要来源交给 Chatnets。

首版不自动生成复杂知识卡片、概念图或大规模长期记忆，也不默认把收听历史全部写入 Chatnets。先积累真实问题，再决定值得沉淀的结构。

## 个人产品定位、内容与版权边界

Castnets 首先是个人收听工具，不以复制播客平台的内容分发、社区和商业网络为目标。

- 优先使用公开 RSS、公开节目元数据、已有公开转写，以及用户有权导入的定时文本。
- 保留节目、音频、转写和补充资料的来源链接与归属信息。
- 不重新托管或公开分发没有授权的完整音频和转写。
- 不绕过付费墙、DRM、登录权限或创作者设置的访问控制。
- 不用合成声音冒充主播或嘉宾，不把模型推断包装成创作者原话。
- 对删除、下架和权利人请求预留清晰的处理路径。
- 未对齐文本不得展示成精确时间引用；资料不足时宁可降级为章节级或“上下文不足”。

M0 的 RSS 抓取只接受 HTTPS feed，并且 feed 地址来自服务端配置，而不是把任意远程 URL 暴露为公共抓取接口。这一安全边界应继续保持。

## 竞品带来的判断

竞品信息会变化。本节记录的是产品判断，不是穷尽式功能清单；进入具体路线决策前应重新核对最新版本。

### Snipd

Snipd 已经证明了以下需求真实存在：耳机按键保存收听片段、AI 转写与摘要、章节、episode chat，以及向笔记工具导出。由此得到的判断是：

- “可以和播客聊天”或“按耳机做笔记”本身不足以构成 Castnets 的差异；
- Castnets 应把差异放在**当前播放时刻的同步打断**、**不使用后文的上下文窗口**、**可连续追问的独立 Branch**和**明确返回原时间线**；
- 中文长对谈的口语、人物关系和语境路由，以及用户自己的 Chatnets 上下文，是需要被实际验证的能力，而不是文案差异；
- 先验证端到端打断体验，不在 M1 追赶导出、摘要库和完整知识管理功能。

参考快照：

- [Snipd 产品页](https://www.snipd.com/)
- [Snipd 价格与功能页](https://www.snipd.com/pricing)
- [Snipd Chat with Episode 发布说明](https://www.snipd.com/blog/chat-with-episode-release)

### 小宇宙

小宇宙是中文播客发现、订阅、播放、分享和围绕具体内容互动的重要体验基准。它带来的判断是：

- Castnets 不应在早期重建内容平台、社交关系或评论网络；
- 应通过公开 RSS 兼容用户已有的节目来源，把有限资源放在“为什么要打断、回答是否贴近此刻、能否顺畅继续”；
- 时间点分享、评论等能力说明“内容与播放位置绑定”对用户有价值，但 Castnets 的 Branch 是一段私人的、可多轮的解释过程，不等同于公开评论；
- 对小宇宙当前功能的具体比较必须在做路线或对外宣传前重新验证，避免以旧版本印象做竞争声明。

参考入口：[小宇宙官网](https://www.xiaoyuzhoufm.com/)

### 总体差异假设

Castnets 要验证的不是“AI 能总结播客”，而是下面这个完整手势是否值得成为新习惯：

> 在正在听的那一句旁边开一条私人对话支线，问清楚，再自然地回到原节目。

如果这一闭环本身没有明显价值，增加更大的模型、更多转写或眼镜入口都不会修复产品问题。

## 当前仓库已经完成的状态

仓库目前包含 M0 后端和 M1 Android 原型。相关里程碑提交为：

- `b9c69be`：Initialize Castnets M0 backend
- `938d62f`：Add Castnets Android M1 prototype

### M0：可运行的本地后端

技术与数据：

- Python 3.11，运行时不依赖第三方包；
- SQLite 持久化 `podcasts`、`episodes`、`content` 和 `branches`；
- 支持 HTTPS RSS 2.0 抓取并映射 Podcast / Episode；
- 内置中文播客“面基”的公开 RSS 作为演示 feed；
- 支持章节、未对齐全文和导入的定时转写。

上下文与 Branch：

- 内容状态分为 `chapters_only`、`transcript_unaligned`、`transcript_timed`；
- 上下文精度分为 `timed`、`chapter`、`none`，并返回相应警告；
- 定时转写只取锚点之前的窗口，不把未来片段交给回答逻辑；
- 未对齐全文只做弱关键词匹配，不伪装成精确时间上下文；
- Branch 绑定 episode 和时间锚点，支持多轮追加；
- 创建 Branch 时计算一次 `max(0, anchor_position_ms - 5000)`；
- resume 使用事务并保持幂等，多次调用不会继续减 5 秒。

接口与限制：

- 提供 loopback-only 的 `/v1` HTTP API 和 OpenAPI 描述；
- 没有认证和 TLS，因此只能用于本机或受控开发连接，不能直接暴露到公网；
- 当前 `MockProvider` 只用确定性术语表返回演示回答，未知概念返回 `insufficient_context`；
- 它不是生产 LLM，也不能用于评价真实问答质量。

### M1：Android 端到端原型

- 原生 Kotlin / Jetpack Compose；
- Media3 ExoPlayer + MediaSessionService；
- 支持音频焦点和耳机断开时暂停；
- 从 M0 `/v1/podcasts` 读取节目和单集，并播放 RSS 音频；
- 用户点击 Ask 后暂停，冻结当前 episode 与播放器位置，创建 Branch；
- 支持文字问题、后续追问，并展示 `spoken` / `visual` 回答；
- 点击 Continue 后调用服务端 resume，并严格 seek 到服务端返回的位置；
- 后端地址可通过 BuildConfig 配置；模拟器默认访问 `10.0.2.2`，真机开发可使用 `adb reverse`；
- 已有 API 映射测试和纯状态机 `ConversationMachine` 测试。

当前 Android 原型仍然是按钮加文字输入。它没有 ASR、VAD、TTS、耳机按键触发、车载交互或眼镜交互。

## 明确未完成、延期或否决的内容

### 未完成

- 生产级服务部署、账号、认证、TLS、权限与隐私控制；
- 数据库迁移和多设备同步；
- 真实 LLM、检索服务、来源引用与答案评测；
- 中文 ASR、VAD、TTS、说话人识别和自动转写对齐；
- Chatnets 个人上下文接入；
- 节目、主播、嘉宾知识层；
- 耳机按键、锁屏/车载交互、连续语音和驾驶安全验证；
- 真机上的完整 M1 验收与长期播放稳定性验证；
- 商业化、创作者后台、内容授权体系和公开社交功能。

### 明确延期

- **耳机输入**：移动端基础闭环验证之后做，是轻交互的下一候选入口；
- **Qwen 眼镜等穿戴设备**：放到第二阶段，只在手机与耳机交互已经证明有价值后评估；
- **唤醒词**：除非真实使用数据证明按键不足，否则不是早期优先项；
- **复杂 Chatnets 沉淀**：先记录真实问题与时间锚点，再基于数据设计结构。

### 明确否决或避免

- 让 AI 冒充真实主播或嘉宾；
- 把章节或未对齐文本伪装成精确时间转写；
- 无差别混合四层上下文；
- 由客户端再次计算或重复扣减恢复位置；
- 在 M0 自研完整 ASR / VAD / TTS 栈；
- 在核心闭环未验证前优先做眼镜、唤醒词或完整社交平台；
- 自动把每次收听生成复杂知识资产；
- 对外重新分发无授权的完整音频或转写；
- 把当前 loopback 开发 API 当作可公网部署服务。

## 下一次最小验证与验收标准

下一步不是扩展功能，而是在真实 Android 设备上证明 M1 闭环可靠。测试应在静止、安全的环境进行，不在驾驶中进行。

### 建议验收流程

1. 本地启动 M0、导入 demo 数据，通过 `adb reverse tcp:8000 tcp:8000` 连接真机。
2. 安装 Android debug APK，选择“面基”或另一个可公开访问的 RSS 单集并开始播放。
3. 播放到已知章节或定时转写附近，点击 Ask，确认音频立即暂停且 episode / 锚点不再漂移。
4. 提交一个 mock 术语问题，确认 Branch 创建、上下文精度与警告正确显示。
5. 追加一次 follow-up，确认仍在同一 Branch，原锚点不变。
6. 点击 Continue，确认只使用服务端 `resume_position_ms`，回退约 5 秒后继续播放。
7. 对同一 Branch 重复调用 resume，确认位置不再继续回退。
8. 验证后台播放、通知控制、音频焦点丢失和耳机拔出暂停。

### 最小通过标准

- 连续完成至少 10 次“播放—打断—问答—继续”而无崩溃、ANR 或 Branch 丢失；
- 锚点与触发时播放器位置的误差不超过 1 秒；
- timed 上下文不包含锚点之后的文本；
- follow-up 保留同一 Branch 和同一初始锚点；
- resume 严格采用服务端返回值，幂等调用不累计回退；
- 网络失败、上下文不足和不可用 RSS 有清晰可恢复的界面状态；
- 后台、音频焦点和耳机拔出行为符合 Android 预期；
- 验收报告明确说明使用的是 MockProvider，不把演示结果写成真实 AI 能力。

完成上述验证后，下一个最小实验应是“硬件按键 + 平台语音输入/输出”的受控原型，先在静止或步行场景验证误触发、响应时延和答案长度，再讨论车载或眼镜入口。

## 新任务启动指南

新 Agent 或开发者开始工作时，先阅读：

1. 本文 `docs/PROJECT_CONTEXT.md`；
2. `README.md`；
3. `docs/architecture-decisions.md`；
4. `castnets/models.py`、`castnets/content.py`、`castnets/service.py`、`castnets/contract.py`；
5. Android 的 `ConversationMachine.kt`、`CastnetsViewModel.kt`、`PlaybackService.kt`；
6. `tests/` 与 `android/app/src/test/` 中的现有测试。

先确认工作区和最近提交：

```bash
git status --short --branch
git log -5 --oneline
```

运行后端测试和离线 demo：

```bash
python3 -m unittest discover -s tests -v
python3 -m castnets --db /tmp/castnets-context-demo.sqlite3 demo
```

运行 Android 验证（需要 JDK 17+ 和 Android SDK 35）：

```bash
cd android
./gradlew testDebugUnitTest lintDebug assembleDebug
```

启动本地 API 的常用命令：

```bash
python3 -m castnets --db data/castnets.sqlite3 seed
python3 -m castnets --db data/castnets.sqlite3 serve --host 127.0.0.1 --port 8000
adb reverse tcp:8000 tcp:8000
```

开始新功能前，先回答三个问题：

1. 它改善的是核心闭环中的哪一步？
2. 它需要四层上下文中的哪一层，来源和权限是什么？
3. 它属于轻交互还是深交互，是否触碰驾驶安全或版权边界？

如果答案不清楚，优先做更小的验证，不扩大系统。提交代码前保持既有用户改动，按风险运行相应测试；除非用户明确授权，不推送远端。
